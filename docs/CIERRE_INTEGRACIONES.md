# CIERRE: fuentes, histórico y sincronización

Auditoría del código disponible al 13 de octubre de 2026. No se ejecutaron consultas reales a proveedores para construir ni probar el módulo, por lo que no se afirma una fecha inicial de histórico que no haya sido comprobada. No se añadieron endpoints de proveedores. Los lectores nuevos reutilizan autenticación y rutas de lectura ya implementadas.

## Fuente utilizada por financiera

| Financiera | Fuente de CIERRE | Histórico disponible | Limitación real |
| --- | --- | --- | --- |
| SUMASPAY | Ventas confirmadas de CONECTAMOS; conciliación en segundo plano con historial de créditos y detalle de un crédito ya identificado. | Ventas locales conservadas y créditos que devuelva el historial de las cédulas conocidas; no hay fecha mínima de retención garantizada en el contrato disponible. | Consultas individuales. La respuesta sólo se reconoce como crédito efectivo si permite identificar el crédito, su capital y su fecha de generación/desembolso. Una aprobación de cupo permanece pendiente. No descubre clientes desconocidos para CONECTAMOS ni demuestra cobertura global. |
| PAYJOY | Ventas confirmadas de CONECTAMOS; conciliación con transacciones `finance` del IMEI conocido. | Ventas locales y transacciones del rango solicitado que conserve la cuenta del proveedor. Se revisan también eventos posteriores del IMEI para recoger reversos del crédito original. | Requiere `financeOrder.id`, `financeAmount` y fecha de la transacción. No hay contrato de paginación ni garantía de que todos los reversos estén presentes. No se usa el saldo pendiente, el precio del equipo, el enganche, ni una consulta de cliente como prueba independiente de generación. |
| ADDI | Ventas confirmadas de CONECTAMOS; observaciones de transacciones para conciliar únicamente los datos que sean inequívocos. | Ventas locales y respuestas por cédula/rango de los dos portales existentes. El cliente actual solicita como máximo 5000 filas por endpoint; no demuestra agotamiento de una paginación. | `APPROVED` no prueba finalización. `createdAt` no tiene semántica de desembolso demostrada en este repositorio. Sólo una transacción con estado efectivo, capital explícito (`creditAmount`, `loanAmount`, `capital`) y `transactionDate` permite adoptar esos datos; de lo contrario se conserva la venta local confirmada y la observación permanece pendiente. |
| SISTECREDITO | Ventas confirmadas de CONECTAMOS, identificadas como fuente local. | Todo el histórico local conservado y cargado por la cola. | No existe cliente de API ni endpoint de créditos SISTECREDITO implementado en el repositorio. No se inventó uno. |
| ALO CREDIT | Ventas confirmadas de CONECTAMOS, identificadas como fuente local. | Todo el histórico local conservado y cargado por la cola. | La integración existente inicia sesión y lee reportes de `admin_reportes`, con complemento de cartera. Está orientada a la semana actual y a créditos recientes; el resultado no expone ID estable ni estado fiable para conciliación histórica. No permite certificar anulaciones ni reversos. |
| FINSERPAY | Ventas confirmadas de CONECTAMOS, identificadas como fuente local. | Todo el histórico local conservado y cargado por la cola. | La consulta por IMEI actual no expone ID estable ni estado, restringe fechas a hoy/ayer y admite alternativas de monto/fecha ambiguas (`montoTotal`, `approvedAt`). No se reutiliza como libro de créditos efectivos. |
| Otras financieras | Ventas confirmadas de CONECTAMOS. | Todo el histórico local conservado. | La cobertura corresponde a lo registrado localmente. Cada aporte de financiera genera su crédito independiente; no se equipara el número de créditos al número de equipos. |

“Histórico local conservado” no equivale a cargado: mientras haya elementos pendientes en la cola inicial o de actualización, el reporte muestra información pendiente. Ninguna consulta individual exitosa acredita que un periodo de un proveedor esté completo.

## Evidencia de las integraciones existentes

- `lib/sumasconsulta.ts`: el historial usa `GET service-credit/manage/core-bridge/credits-by-client/all?identification=...`; un ID previamente vinculado permite leer `GET service-credit/manage/loan/:id`. El lector de CIERRE no llama `client/pos`, los asistentes de elegibilidad ni `pay/plan`. El helper mensual previo mezclaba fuentes, omitía el estado y aceptaba campos como `approvedPrincipal`; por eso no se reutiliza para decidir efectivos.
- `lib/payjoy-retail.ts`: `GET list-transactions.php` ya acepta `starttime`, `endtime` y `filter=device.imei:...`. CIERRE conserva la identidad de `financeOrder.id` y utiliza exclusivamente `financeOrder.financeAmount`. No utiliza el fallback a `transaction.amount` ni `lookup-customer.php`. `lib/payjoy.ts` proporciona datos de cuotas/saldo mediante la página de pagos; esos datos no forman el cierre de créditos generados.
- `lib/addiconsulta.ts`: los endpoints existentes son `/transactions` de `ally-portal.addi.com` y `/v1/transactions` de `ally-portal-external-api.addi.com`. El lector de CIERRE conserva estados al omitir el filtro `status=APPROVED`. No supone que los endpoints acepten un cursor nuevo ni que una respuesta corta garantice completitud. El helper mensual previo eliminaba estados y aceptaba `price`, `amount` y `updatedAt`; esos fallbacks no se adoptan como capital/fecha efectiva.
- `lib/aloconsulta.ts` y `lib/alo-report-parser.ts`: lectura de reportes con selección de fechas recientes, importes por encabezados y, en ciertos reportes, columna heredada. El tipo devuelto no contiene ID/estado de crédito. Se mantiene la fuente local en CIERRE.
- `lib/finserpayconsulta.ts`: la ruta existente es `/api/public/creditos/imei` o la URL configurada; el tipo devuelto carece de ID/estado de crédito y la consulta no ofrece un listado de periodo. Se mantiene la fuente local en CIERRE.
- No se encontraron contratos implementados de webhook, verificación de firmas o cursor incremental de proveedores para estas seis financieras. Por ello no se publica un webhook sin autenticación ni se simula una sincronización incremental del proveedor.

## Lectores estrictos y trazabilidad

`lib/cierre-providers.ts` expone `consultarLoteProveedorCierre`. Cada ejecución admite una referencia y no realiza reintentos ocultos ni fanout de cédulas/IMEI. Los clientes comprueban configuración antes de consultar. Los proveedores con fuente local no hacen llamadas externas.

El resultado conserva financiera + ID estable, principal, fecha efectiva, estado, identidad mínima del cliente y evidencia reducida del criterio de clasificación. No persiste tokens, credenciales ni el payload completo de clientes. Los estados normalizados son `EFECTIVO`, `ANULADO`, `REVERSADO`, `RECHAZADO` y `PENDIENTE`. Un cierre de cuenta sin significado demostrado (`CLOSED`, por ejemplo) no se interpreta automáticamente como anulación. Un crédito pagado sigue siendo un crédito generado.

Para PAYJOY, el evento de reverso actualiza el crédito por su ID y conserva la fecha original de financiación; la fecha del reverso nunca pasa a ser fecha de generación. Para SUMASPAY se prioriza una fecha real de desembolso sobre la fecha de creación. Para ADDI se exige `transactionDate`, porque no se pudo demostrar la semántica de `createdAt`. Todas las fechas sin zona explícita se interpretan en `America/Bogota`.

El enlace inicial con una venta local requiere coincidencia inequívoca de financiera, principal, fecha y documento/IMEI. La identidad persistente posterior es financiera + ID del proveedor; la cédula por sí sola no deduplica créditos. Un crédito de API sin sede inequívoca permanece pendiente de conciliación y no se suma a una sede atribuida por suposición. Una observación desconocida o una aprobación no reemplaza un hecho confirmado local.

El esquema previo de `Venta` conserva importes por financiera, pero no números de préstamo. Por eso los registros exclusivamente locales muestran “Sin número registrado”; nunca se presenta el ID de venta como número de crédito. Dos créditos del mismo cliente en ventas distintas se conservan separados. Si una venta antigua agrupó varios préstamos de la misma financiera en un único importe, el dato anterior no permite reconstruir cuántos préstamos fueron: se conserva un aporte local y la conciliación remota queda pendiente cuando no hay un enlace único. Los registros de asesor pendientes no crean créditos en el cierre.

## Operación y carga inicial

1. Aplicar la migración `scripts/apply-cierre-schema.sql` con el procedimiento de despliegue del proyecto y regenerar Prisma. La migración prepara las tablas y la cola de ventas existentes; no consulta proveedores.
2. En el despliegue Node/standalone, configurar `CIERRE_SYNC_ENABLED=1`: `instrumentation.ts` inicia el trabajador al arrancar, con exclusión mutua en PostgreSQL entre réplicas. Mientras quedan ventas listas para procesar, continúa con una pausa de 1,5 segundos entre lotes; cuando termina, encuentra sólo reintentos diferidos o falla, espera un minuto. Requiere un proceso Node persistente; no supone ejecución permanente en entornos serverless.
3. Como alternativa para entornos con un programador externo, configurar `APP_URL` y `CRON_SECRET` en ese proceso y el mismo `CRON_SECRET` en la aplicación; programar `node scripts/sincronizar-cierre.mjs` cada minuto. Llama al endpoint interno `POST /api/cierre/sync`, autenticado con secreto. La existencia del archivo no acredita que el programador externo esté activo. No es necesario activar los dos mecanismos.
4. El trabajador procesa hasta 500 ventas o 30 segundos por lote local y conserva el avance en la base de datos. Cuando varias ventas comparten la fecha de entrada inicial, procesa primero los IDs recientes. Los cambios posteriores de ventas vuelven a entrar en la cola. Una interrupción permite reanudar sin eliminar el histórico anterior. Cada lote exitoso actualiza la fecha de avance; eso no certifica que se haya completado el histórico.
5. Para activar la conciliación externa, configurar los clientes existentes y `CIERRE_PROVIDER_SYNC_ENABLED=1`. La carga local funciona independientemente de ese interruptor. El interruptor mantiene desactivadas las llamadas externas hasta que el despliegue haya establecido los límites/costos contractuales: el repositorio no documenta tarifas ni cupos de consulta de los proveedores.
6. El trabajador procesa como máximo una referencia de proveedor por ejecución autorizada para ello. El programador mantiene al menos un minuto entre esas oportunidades; los lotes locales adicionales omiten proveedores. Conserva exclusión mutua, avance persistente, reintento con espera y revisión posterior. Nunca se dispara desde abrir CIERRE, modificar filtros, abrir detalle o exportar.

Los GET del reporte, detalle y Excel leen exclusivamente el libro local. Los totales y el detalle usan el mismo periodo y la misma restricción de sede; el límite de diez filas se aplica sólo a la página del detalle, no al total ni al Excel.

La cobertura local se calcula para el periodo y la sede autorizada. Una actualización pendiente revisa la venta actual, el crédito anterior y el snapshot de la cola: mover o eliminar una venta mantiene pendientes los ámbitos afectados. Los pendientes de otros meses o sedes no impiden completar el periodo consultado. Mientras esa carga local continúa, la pantalla vuelve a leer el reporte y el detalle cada diez segundos, muestra el avance y confirma la consulta; nunca inicia sincronizaciones ni cambia filtros sin aplicar.

Los tres adaptadores externos devuelven `complete: false`: las referencias locales, los límites de los endpoints y la falta de un censo/paginación verificada no permiten certificar un periodo completo del proveedor. Una respuesta vacía, un error, una integración no configurada o un trabajo pendiente nunca se convierten en un cero confirmado.

## Verificación realizada

Las pruebas de `tests/cierre-providers.test.mjs` utilizan respuestas sintéticas e inyección de lectores; no consumen APIs reales. Cubren capital sin inicial/precio/cuotas, aprobaciones sin crédito, IDs duplicados, varios créditos por cliente, anulaciones/reversos/rechazos, créditos pagados, fechas Bogotá, límites de periodo, histórico parcial, configuración ausente y ausencia de llamadas en financieras de fuente local. Las pruebas del dominio/servidor complementan filtros, asociación local, paginación y permisos.

Queda como validación de despliegue constatar las credenciales, programador activo, respuesta real de cada cuenta y periodo más antiguo que efectivamente devuelve el proveedor. Hasta entonces no hay una fecha de inicio del histórico remoto ni cobertura completa certificadas.

La validación local no requiere `DATABASE_URL`: las pruebas de servidor usan un doble de Prisma y generan/leen un archivo Excel real; la verificación visual utiliza datos simulados. Para activar en el entorno configurado: `npm run db:apply-cierre`, `npm run prisma:generate` y habilitar uno de los trabajadores descritos arriba. La migración debe aplicarse completa, porque `prisma db push` por sí solo no crea los triggers de la cola.

El despliegue ejecuta la migración antes de arrancar la nueva versión. Es transaccional y reanudable, con espera de bloqueo limitada a diez segundos y límite de dos minutos por sentencia; un fallo impide publicar una versión sin sus tablas. El trabajador omite la fase de compilación y registra únicamente contadores de avance (`CIERRE_SYNC`), sin datos personales, para verificar la carga real. El despliegue inicial habilita la carga local y mantiene desactivadas las consultas externas.
